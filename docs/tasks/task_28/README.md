# Task 28 - Restore the 7 → 8 database migration

Fixes audit finding C3 ([task_25](../task_25/README.md)).

## Problem

`AppDatabase` declared only `AutoMigration(8, 9)`. The `AutoMigration(7, 8)`
that adds the v2 tables was replaced rather than kept when 8 → 9 was added in
7948ac51 (2022-08). There is no destructive fallback, so no install from the
1.x releases can upgrade to 2.2.

Every 1.x release shipped schema 3, 4 or 6. Their only route to 9 is
3/4/6 → … → 7 → 8 → 9, so without the 7 → 8 link Room finds no path. A 1.4.0
install (schema 6) throws
`IllegalStateException: A migration from 6 to 9 was required but not found`
on its first DB access, on every launch. Its unsynced trees stay stuck until
the user clears app data, which deletes them.

- `7.json` has not changed since 2020.
- `8.json`'s identity hash (`289bc674…`) is the same today as in the 2.0.0
  release build. Restoring `AutoMigration(7, 8)` therefore regenerates the same
  migration that 2.0.0–2.1.3 shipped.
- `release-2.1.3_candidate-2` already declares both auto migrations.

## Changes

- `AppDatabase`: re-add `AutoMigration(from = 7, to = 8)` with a comment
  explaining why it must stay.
- `AppDatabase.builder(context, name)` (internal) holds the app's database
  configuration, including the now-private list of hand-written 3 → 7
  migrations. `getInstance()` and the migration test both open the database
  through it, so the test checks exactly what the app runs.

## Tests

`AppDatabaseMigrationTest` (Robolectric):

- **How it works:** it builds a DB file straight from an exported schema JSON,
  then opens it through `AppDatabase.builder`, the same configuration the app
  uses. Opening runs the migrations, and Room validates every migrated table
  against the current entities. `MigrationTestHelper` isn't used because it
  reads schemas from instrumentation assets, which unit tests here don't have
  (`includeAndroidResources` is off outside Roborazzi runs).
- **`schema 6 (the 1_4_0 release) upgrades to latest and keeps unsynced legacy
  trees`:** seeds a planter, a check-in and an unsynced `tree_capture` at schema
  6, the real 1.4.0 schema (`6.json` matches `release-1.4`). It then upgrades
  through 6 → 7 → 8 → 9. Afterwards the tree is still pending upload and the v2
  tables exist. Without the restored line it fails with the production crash
  message, `A migration from 6 to 9 was required but not found`.
- **`every exported schema from version 6 upgrades to latest`:** covers 6, 7
  and 8. The current version is skipped, because its JSON is regenerated by
  every build and so opening it can't fail.

## Not in scope

- Schemas 1-4 can't be tested from their JSON. `1.json`-`4.json` don't
  describe the databases that shipped: `d820c63e` rewrote the 3 → 4 and 4 → 5
  migrations for production without re-exporting them (e.g. `3.json` already
  has `planter_info`, which `MIGRATION_3_4` creates), and `5.json` is missing.
  Testing the 1.2.7 and 1.3 paths would need a hand-built fixture.
- There is still no migration from 1 → 2 or 2 → 3.

## Device validation

On the emulator I built a schema-6 database from `6.json` (identity hash
`5eeb9e62…`, the same as on `release-1.4`): one unsynced 1.4.0 tree, plus its
planter and check-in. I pushed it into the debug app with `run-as`.

- **`master` (pre-fix):** crashes at launch with `IllegalStateException: A
  migration from 6 to 9 was required but not found`.
- **This branch's build, same database:** launches normally. The pulled DB has
  `user_version = 9` and all the v2 tables plus `organization`. The 1.4.0 tree
  is intact (`tree-from-1.4.0`, `uploaded = 0`).

An earlier run from a hand-built schema-7 database showed the same crash
("from 7 to 9") and the same fix. Only beta builds ever had schema 7, though.
